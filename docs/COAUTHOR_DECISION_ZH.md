# 共同作者 vs 引用 — 決策懶人包(2026-11-08)

> 給誰看:指導老師、DATE 稿一作(rank-3 隊)、我。目的:在 **11/11(DAC 作者名單
> 與摘要鎖定)**前把掛名、引用、合規、稽核實驗四件事一次談定。

---

## 0. 背景:兩篇論文的關係(30 秒版)

| | 我們的 DAC 稿 | 他的 DATE 稿(審稿中,11/23 放榜) |
|---|---|---|
| Testbed | ICCAD 2026 Problem A(同一個) | 同左 |
| 系統 | 封閉世界 intent 路由 + 三道 guard(fail-closed) | ReAct 工具迴圈 + 四個 task-completion 檢查 |
| 核心主張 | **不安全的改動出不去**(架構保證)+ 小模型路由極限的量測 | **沒做到要求的事藏不住**(等價 ≠ 完成) |
| 互補點 | 我們誠實承認的 drift 缺口(等價但不如所求) | 正是他的檢查所針對的層 |

貢獻不重疊、互為拼圖——無論掛名與否,**互相引用都對兩篇有利**。

## 1. 兩條路線的比較

### 路線 A:純引用 + 致謝(不掛名)

- 我們引用他的工作(跨架構證據、related work、drift 互補),他提供 rank-3 官方
  分數 → 寫進 Acknowledgment:「感謝 X 提供……」。
- ✅ 學術上最乾淨;引用本來就是「使用他人成果」的正規管道;提供一筆資料屬致謝等級。
- ❌ 他沒有名分;若未來兩篇合併成期刊版,合作基礎較弱。

### 路線 B:掛二/三作(老師初步傾向)

- **成立條件**:作者資格要求「對本文的實質智識貢獻」。只靠「我們引了他 + 他給分數」
  構不成——那叫 **gift authorship**,IEEE/ACM 規範明確反對;contest 相關論文在
  camera-ready 揭露後(rank-1 + rank-3 兩隊同列作者)容易被檢視,必須經得起
  「他貢獻了什麼」的質問。
- **讓掛名名正言順的做法:§3 的稽核實驗**——具體、可驗、工作量 1–2 天,做了就是
  教科書等級的作者貢獻(本文一節實驗由其框架執行 + 共同撰寫相關章節)。
- ✅ 多一位熟 benchmark 的作者分攤 11/18 前的衝刺(英文稿、校對);資料提供變成
  「作者自有資料」,乾淨;為期刊合併版鋪路。
- ❌ 若稽核實驗沒做成,掛名理由退回 gift authorship 風險。

### 建議決策規則(一句話)

**他做稽核實驗(或同等實事)→ 路線 B;只能給分數和授權引用 → 路線 A。**
11/11 前必須定案,作者名單鎖定後不可增補。

## 2. 無論選哪條都要辦的合規事項(DAC 官方規定,dac.com 已核實)

1. **自引一律第三人稱**;參考文獻**禁止** "omitted for blind review"。
2. **強制揭露**:DAC 投稿系統有「相關未發表工作」程序——把 DATE 稿 PDF 交給
   TPC Chair 私下核對(不給審稿人看)。**未揭露密切相關工作 = 拒稿 + 可能上報
   IEEE/ACM。** 兩篇同 benchmark、(可能)共同作者,百分之百屬於必揭露。
3. **建議他把 DATE 稿掛 arXiv**(預印本,上傳 ≠ 發表、不影響 DATE 資格,但需他
   確認 DATE 雙盲政策與個人意願):掛了我們才有可引用的公開文獻,正文以第三人稱
   引用;不掛則走 B 方案(正文泛稱 concurrent work + 揭露程序,camera-ready 補引,
   論證力道略減)。
4. PDF metadata 清洗、匿名化掃描(兩隊身分、分數可反查處)投稿前統一執行。

## 3. 稽核實驗設計(路線 B 的貢獻主體;實驗代號 E15)

### 一句話

**用他的四個 task-completion 檢查(離線模式),稽核「我們的 agent」在 40 個公開
測資上錄製的完整 trace**——我們的 drift 主張獲得獨立第三方量化,他的框架獲得
「審過第二個異質架構」的通用性證據,雙贏。

### 為什麼可行

他的論文明寫:四個檢查可在 recorded trace 上離線執行,輸入只需——每個 request 的
邊界、回應文字、回傳網表、匯出檔案;不需要接觸我們的 agent 程式。

### 分工與交付物

| 步驟 | 誰 | 內容 | 估時 |
|---|---|---|---|
| 1. Trace 打包 | 我方 | 重錄 40 公開測資(規則模式、本地、免 API):每 case 的 request 序列、逐 request 回應(#RESPONSE frames)、**每次 edit 後的網表快照**、final 匯出檔;附格式說明 README | 半天 |
| 2. Adapter + 跑檢查 | 他 | 寫小轉接器讀我們的 trace 格式 → 跑四個檢查 → 輸出逐 request 判定(requested-edit / active-constraint / reported-fact / export)與 corrections | 1–2 天 |
| 3. 寫進論文 | 我方(他共審) | §4.6 新增「independent task-completion audit」小段:459 個 request 中多少被判 incomplete、其中多少屬 drift 類、與我們 fault-injection 的 drift 率(7/24)對照 | 半天 |

### 時程

trace 打包 11/9 → 他跑 11/10–11 → 寫進稿 11/12 → **11/15 前凍結**,留三天 buffer
到 11/18 全文截止。

### 風險與事先講好的原則

- **稽核可能挖出我們 agent 的新問題** → 照兩篇論文共同的哲學:誠實報告。這不是
  風險而是加分(審稿人最信「自己報自己瘡疤」的系統論文);若發現可修的 bug,
  修掉並報 before/after。
- 格式對不上 → 我方負責轉格式(我們的 log 本來就含 #RESPONSE 框架,網表快照
  可由 evaluator in-process 模式重錄)。
- 他的時間不夠 → 降級為路線 A,引用照常,不傷感情——**先把這條退路講明白**。
