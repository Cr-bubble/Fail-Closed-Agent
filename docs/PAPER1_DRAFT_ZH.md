## 摘要

自然語言介面正在進入 EDA 工作流,但真實部署面臨兩個同時收緊的約束。其一,晶片
設計資料是高度機密的 IP:網表不宜送往雲端 frontier 模型,模型選擇實際上被鎖在
可本地部署或 mini 級的小型凍結模型;其二,網表的功能正確性是硬限制而非品質分數:
如同 sign-off 的 LEC 門檻,一份功能被改壞的設計靜默流入下游,代價是災難性的。在
這個「小模型 × 硬性正確」的 regime 裡,主流「LLM 產出 artifact、事後驗證把關」的
代理架構把正確性押在驗證覆蓋率上,並不可靠。我們提出 fail-closed 架構:LLM 被
限縮為「一句自然語言 → 一個封閉世界 intent」的翻譯器,約 80 個經 schema 驗證的
intent 表達不出任何不安全的操作;所有電路分析與改寫由確定性引擎執行,每次網表變更
必須通過功能等價(register-cut CEC)、結構界限與 basis 純度三道檢核,否則回滾。
幻覺的損害因此被結構性地封頂於「路由錯誤」。我們以 ICCAD 2026 CAD Contest
Problem A 為 testbed——它恰好把上述兩個約束形式化(指定凍結 mini 模型;任一硬性
違規即整題零分)——在 1,420 條真實請求上做控制變因研究,回答「小型凍結模型的
路由準確率究竟被什麼限制」:catalog-only 的 gpt-4o-mini 為 88.4%(五次重跑全距 0.4);
檢索的價值取決於例句庫品質與模型——弱庫(recall@50=82%)對 gpt-4o-mini 僅值
+0.5 點、換高召回庫 +6.4 點,而 claude-haiku-4.5 在同一弱庫上即達 97.4%:召回率與
端到端的脫鉤成立、但有條件;同庫同設定下換模型值 +8.5 點;瓶頸始終是近義 intent
的辨別;監督式分類器最高僅 73.3%,無法取代 LLM。fault-injection 實驗顯示 24/24 的污染注入皆未造成不安全
commit。所有量測配備效度遙測(曾兩度攔截 API 靜默降級製造的假分數,§4.7)。系統於
testbed 的 231 個官方測資(公開/beta/final)維持零硬性違規;與公開榜單的總分
比較見 §5。

## 1. Introduction

自然語言介面正在快速進入 EDA 工作流:對話式設計問答、工具腳本生成、RTL 自動修補。
但把這類介面推向真實設計環境時,兩個約束同時收緊。第一,**模型能力被鎖在小模型
一端**:晶片設計資料是企業最核心的機密 IP,網表與設計意圖不宜離開內網(ChipNeMo
的 on-prem 部署動機正在於此),互動式工作流又要求每句低延遲、低成本——現實的選項
是可本地部署或 mini 級的小型**凍結**模型,而非雲端 frontier 模型;持續 fine-tune
的維運管線在多數團隊也不存在。第二,**正確性是硬限制,不是品質分數**:在生產 flow
裡,等價性如同 sign-off 的 LEC 門檻,一份功能被改壞的網表流入下游的代價是災難性
的——最危險的失敗模式不是代理答錯問題,而是它**靜默地**改壞設計並回報成功。

這個「小模型 × 硬性正確」的 regime 恰好打在主流代理架構的弱點上。既有的 LLM-EDA
代理共享一個結構:讓 LLM 產出某種 artifact——工具呼叫腳本(ChatEDA)、修補後的
RTL(RTLFixer)、或直接生成的程式碼(VerilogEval 一系)——再以編譯器或測試做
事後檢查。事後檢查能發現錯誤,但錯誤**有路徑到達成品**;小模型更高的錯誤率放大了
這條路徑的流量,凍結模型又封死了「用 fine-tune 壓錯誤率」的出路。在硬性正確的
環境裡,「先產出、後驗證」等於把系統的正確性押在驗證的覆蓋率上。那麼,這種 regime
裡的代理應該長成什麼樣子?

ICCAD 2026 CAD Contest Problem A(LLM 輔助網表探索與改寫)把這個 regime 形式化成
一個可量測的 testbed:系統從標準輸入逐行接收**不限句式**的自然語言請求,在一份
持續演化的 gate-level Verilog 網表上執行分析(深度、cone、路徑、等價性)、結構
改寫(buffer 插入、basis 轉換)與最佳化(深度/閘數),以 lock-step 協定逐行回覆,
設計狀態跨請求累積。主辦方指定僅能使用兩個凍結的 mini 級模型(gpt-4o-mini 與
claude-haiku-4.5)、不允許 fine-tune;計分 all-or-nothing——任何一個硬性要求被
違反,整個測資歸零並連坐其後所有請求。本文以它為評測載體:它的兩條規則正是上述
兩個現實約束的實例化。

我們的答案是把架構倒過來:**LLM 是翻譯器,不是推理器**。LLM 的唯一職責是把一句
自然語言翻譯成一個 intent 物件,而這個物件活在封閉世界裡——約 80 個經 schema 驗證
的 intent、必選/可選參數皆有型別與枚舉約束,**表達不出任何不安全的操作**。所有電路
工作由確定性引擎完成;每一次網表變更在 commit 前必須通過三道檢核:register-cut 的
組合等價證明(對本任務的 DFF 模型是 sound 的時序等價)、結構界限重算、basis 純度
檢查,任一失敗即回滾至變更前快照。幻覺的損害因此被**結構性地**封頂:最壞情況是
路由錯誤(答錯一題),而非交出一份功能被改壞的設計(整題歸零並連坐)。

架構保證了正確性之後,一個乾淨的科學問題浮現:**小型凍結模型的路由準確率究竟被什麼
限制?**我們在 testbed 的 1,420 條真實請求上,以 leave-one-testcase-out 協定做
控制變因研究,得到幾個與直覺相左的量測結果:(i) 檢索召回率與端到端準確率的關係
**取決於模型**:claude-haiku-4.5 在 recall@50 僅 82.1% 的例句庫上仍達 97.4%(脫鉤
成立),gpt-4o-mini 則對庫品質敏感(高召回舊庫 95.1/95.6(N=2)vs 弱庫 88.9,+6.4 點);
(ii) 同庫同設定下換模型值 **+8.5 點**(97.4 vs 88.9),比任何檢索工程大一個數量級;
(iii) 73–99% 的失敗案例中,正確 intent 其實已在 context 內【歷史值】——瓶頸是
近義 intent 的辨別,不是檢索;(iv) 監督式分類器(TF-IDF + LinearSVC,用盡全部標註
資料)最高 73.3%(語義 embedding 亦僅 72.8%),低於部署組態 LLM 達 15.6–24.1 點,無法取代;(v) regex 優先的混合路由可能
比純 LLM 更差【歷史值】,因為誤攔截的請求永遠到不了 LLM。

這些量測受一層效度工程保護:我們曾記錄 API 靜默降級把基礎設施失敗偽裝成模型
失敗、產出看似合理的 67.2% 假分數(真值 97.8%);降級計數與無效輪判定其後兩度
在真實情境中攔截同類事故(§4.7)。

系統端到端的結果:231 個官方測資(40 公開 + 91 beta + 100 final)零硬性違規,
輸出皆經 ABC 驗證等價;beta 僅有的失分來自後經官方 ruling 釐清的語意歧義,final
失分僅餘最佳化成本比(§5);fault-injection 實驗中 24/24 的污染注入皆未造成不安全
commit。【匿名注意:投稿版不印本隊官方總分,僅引公開榜單;camera-ready 揭露】

## 2. Background 與相關工作

**LLM-EDA 代理。** ChatEDA 以 fine-tune 過的模型(AutoMage)規劃並產生 EDA 工具
呼叫腳本;Ask-EDA 與 ORAssistant 做文件導向的 RAG 問答;RTLFixer 讓 LLM 迭代修補
RTL 並以編譯器回饋收斂;VerilogEval 與 RTLLM 評測 RTL 程式碼生成。這些工作中 LLM
的輸出——腳本、程式碼、修補——都是成品的一部分,錯誤經事後檢查攔截,但攔不住的
部分直接進入成品。本文的架構相反:LLM 輸出被關在一個表達不出不安全操作的封閉世界。

**工具呼叫與檢索。** Gorilla、ToolLLM 與 Berkeley Function Calling Leaderboard
研究 NL → API 呼叫的翻譯,典型做法是檢索 **tool 文件** 進 prompt。我們實測此路線
在本任務的 label-recall 天花板為 65.4–75.1%【歷史值】,甚至低於無檢索 baseline;
而檢索「已標註**例句**」可達 97.5%【歷史值】。此外,這些系統沒有「對活狀態的
grounding」:本文的管線會把 LLM 填入的名稱型參數對照**當下已被改寫過的網表**驗證,
不存在即帶錯誤回饋重譯。

**Generate-and-verify。** LLM-Modulo 一系主張 LLM 生成、外部驗證器把關。本文可視
為該思想在 all-or-nothing 計分領域的完整系統落地與端到端量化——並額外回答了「驗證
器把關之後,生成端的誤差結構長什麼樣」。

## 3. 系統:Fail-Closed 架構

【Fig.1 placeholder:系統架構——LLM(封閉世界翻譯)/ 確定性引擎(分析‧轉換‧
最佳化)/ 三道 guard + 回滾 / 協定層;可與 Fig.2 合併為雙 panel】

### 3.1 封閉世界 intent contract

系統定義約 80 個 intent,涵蓋分析(計數、深度、cone、路徑、連通性、功能性質)、
轉換(basis 重映射、buffer 插入、清理、改名)與最佳化(深度/閘數)。每個 intent
有必選與可選參數的 schema;枚舉型參數(basis、方向、模式等)有封閉值域。完整的
intent catalog——含每個 intent 的說明與**近義 intent 的消歧區塊**——以約 10,280
tokens 常駐於 system prompt 的固定前綴,經 prompt cache 攤銷(token 成本約 −79%)。

關鍵設計:**catalog 永遠全量在場**。檢索(§3.2)只負責往 prompt 增補相似例句,
永遠不裁剪 intent 清單本身——因此任何檢索失敗的代價只是幾個無用的示範,**不可能把
正確答案移出模型的可及範圍**。我們把這個原則總結為:*retrieve demonstrations, not
the tool list*。它的量化後果見 §4.3 與 §4.5。

同樣關鍵的是把「封閉」說精確:**封閉的是操作空間,不是表達力**。每個 intent 是
預先實作、逐項測試過的確定性程式,但參數空間是開放的——作用在哪條 net、哪個
cone、數值界限多少、哪組 basis,都由每一句現場決定,且名稱型參數還必須通過對
「活網表」的存在性驗證(§3.2)。落在 catalog 之外的請求也有**定義好的行為**:
安全 no-op(回覆「設計不變」)——寧可不做,也不亂做,這正是 fail-closed 的
「closed」。catalog 的範疇來自任務規格列舉的操作類型;擴充它是「加一個 handler
+ schema + 消歧條目」的工程維運,逐項可單測、可審計,而非重新訓練模型。

### 3.2 Routing pipeline

【Fig.2 placeholder:五階段管線圖,標注每階段的失敗出口都是 fail-closed】

一條請求經過五個階段:

1. **翻譯**:LLM 收到固定 catalog(cached)+ 動態增補的 BM25 top-50 相似例句
   (自 940 列的已標註例句庫檢索;庫內 531 個 unique (text, op) 配對;評測時
   leave-one-testcase-out),輸出一個 JSON intent 物件。
2. **語法驗證**:`validate_intent_object` 檢查 intent 是否存在、必選參數是否齊備、
   枚舉值是否合法;失敗時把**拒絕原因**回饋給模型重選一次。
3. **語意 name-grounding**:凡應指涉真實 net/gate 的參數,對照**當下**網表檢查
   存在性;指到不存在的名字即帶錯誤訊息重譯。這一步 grounding 在「活的、已被先前
   請求改寫過的設計狀態」上,是現有 tool-use 系統普遍缺少的。
4. **Dispatch**:路由到確定性 handler。分析類直接在 IR 上跑圖演算法;變更類進入
   §3.3 的 commit 紀律。
5. **快取**:同一句子在單輪內的翻譯結果被快取,壓制 temperature 噪音。

全部階段失敗時,系統回覆安全的 no-op 確認(「設計不變」)——fail-closed 的預設。

### 3.3 Guards 與 commit 紀律

每一次網表變更在 commit 前必須通過三道檢核,任一失敗即回滾至變更前快照:

1. **功能等價**:以 register-cut 把時序電路投影為組合電路——每顆 DFF 的 D、CK、
   RN、SN 全數成為 pseudo-PO,Q 成為 pseudo-PI——再交 ABC `cec`。由於 DFF 的全部
   輸入皆被投影為可觀測點,組合等價即為 sound 的時序等價(含 clock 與非同步腳上
   有邏輯的情形)。
2. **結構界限**:該請求若載明界限(如 fanout ≤ k),以獨立重算確認。
3. **Basis 純度**:該請求若限定閘型(如僅 NAND/NOT),檢查結果網表的閘型集合。

變更同時記入 delta 帳(插了幾顆 buffer、刪了幾個 gate),使後續「How many X were
added?」類請求有確定性的資料來源。

### 3.4 損害上限論證

在這個架構下,LLM 的任何輸出——包括徹底的幻覺——只能造成兩種後果:(a) 路由到
錯誤的分析 intent,答錯一題;(b) 路由到錯誤的變更 intent,而該變更要嘛通過三道
檢核(安全,雖可能非用戶所求)、要嘛被回滾(設計不變)。**不存在「功能被改壞的
網表離開系統」的路徑**。這個主張的邊界與實證檢驗見 §4.6:fault-injection 曾找到
唯一的例外(改名撞既有名稱,一個未走 guard 的操作),經一行修正後,24/24 的注入
皆無不安全 commit,主張成為 exact。

## 4. 量測研究:路由準確率被什麼限制?

### 4.1 協定

評測集為 testbed 的全部 1,420 條真實請求(test101–171,71 個 intent),每條附人工標註的
(intent, params) 真值;檢索庫為獨立的 940 列公開例句庫。全程 leave-one-testcase-
out:查詢句自身測資的例句不得進入 prompt。指標:intent 準確率(主)、params
準確率、完整物件準確率。單輪內部以 8–12 並發執行,但**不同評測輪嚴格串行**
(理由見 §4.7)。變異數:gpt-4o-mini 兩個 headline 設定已各 N=5(全距 ≤0.6 點,E4);legacy 庫 N=2;haiku 目前 N=1(E4 續跑中)。

### 4.2 Ablation ladder

【Fig.3 placeholder:雙軌階梯——bare 61.4(gpt)/78.7(haiku)→ catalog 88.4 → +BM25 k50 88.9 →
換高召回庫 95.1 → 換 haiku 97.4;legacy 時代 ladder(86.9→94.3→95.3)以淡色對照】

固定 catalog、逐級加入機制(2026-11 重測):

| 設定 | intent 準確率 | N |
|---|---|---|
| 裸 LLM(僅 intent 名稱清單),gpt-4o-mini | **61.4%** | 1 |
| 裸 LLM(僅 intent 名稱清單),claude-haiku-4.5 | **78.7%** | 1 |
| 完整 catalog(無檢索),gpt-4o-mini | **88.4%**(88.3–88.7) | 5 |
| + BM25 k=50,production 庫(recall@50 82.1%) | **88.9%**(88.6–89.2) | 5 |
| + BM25 k=50,legacy 高召回庫(recall@50 96.4%,LOCO) | **95.1 / 95.6%** | 2 |
| claude-haiku-4.5 + BM25 k=50,production 庫 | **97.4%**(歷史 pre-dedup 97.8) | 1 |

歷史 ladder(86.9 → +消歧 ~89.5 → +k25 94.3 → +k50 95.3)是在 legacy 庫時代量的
【歷史值】;本輪重測確認 95.3 在其自身組態下可重現(95.1/95.6,N=2,夾住歷史值 95.3),而組態切到
production 庫後、檢索對 gpt-4o-mini 的增益縮為 +0.5 點——**檢索庫品質是被歷史
紀錄隱藏的一個 ablation 維度**(§4.3)。catalog 工程本身(說明+schema+消歧)值
**+27.0 點**(gpt,61.4→88.4);裸模型下 haiku−gpt 差 +17.3 點、完整管線下縮為
+8.5 點——**管線對弱模型的補強更大**。k 掃描(E5):production 庫上 k=5→100 僅
88.1–89.4(非單調、全距 1.3 點,召回率同期 60%→86%),k 在弱庫上是非變數。

catalog-only 的細部:safe 類(載入/輸出/計數)355/355 = 100%,hard 類 84.7%;
params 準確率 84.6%、完整物件 80.1%。163 個失敗中 50 個 give-up、113 個 wrong-op,
top 混淆為 pi_to_po_depth→global_max_depth(11 次)與 check_floating→
check_dangling(10 次)——全部是近義 intent 家族。兩段修正的歷史效果:give-up 從
107 → 3,wrong-pick 從 79 → 28【歷史值】。

### 4.3 檢索分析:召回率與端到端脫鉤

【Table 1 placeholder:檢索後端 × recall@k × e2e × 延遲;**兩個 bank 分欄標示**】

檢索數字必須標明例句庫:歷史量測(六後端比較、recall 93.9@25 / 96.4@50、union
98.7@50)是在**舊評測庫**(examples.jsonl,2,130 列,LOCO)上做的【歷史值】;現行
**production 庫**(public, 940 列)上的新量測為:BM25 recall@5/10/25/50/100 =
60.2 / 66.5 / 76.3 / 82.1 / 85.6%,首個正確 op 的中位 rank = 2,14.4% 的查詢在
k=100 內完全撈不到正確 op,其中 3 個 intent(60 句,4.2%)在庫中**零樣本**、對檢索
結構性不可達。查詢延遲 mean 0.52 ms / p95 0.99 ms(純 stdlib,零依賴)。

脫鉤是**有條件的**,而條件本身是發現:(i) claude-haiku-4.5 在 recall@50 僅
82.1% 的 production 庫上達 97.4%——檢索漏掉的由常駐 catalog 接住(§3.1 的設計
紅利),對夠強的小模型,召回率確實與端到端脫鉤;(ii) gpt-4o-mini 暴露另一面:
同是 k=50,庫從 production 換成高召回 legacy(recall 82.1%→96.4%),端到端
88.9%→95.1/95.6(+6.4 點,N=2)——**對更弱的模型,檢索品質重新變得重要**(注意 legacy
庫含與評測句同分布的標註例句,只能以 LOCO 作量測上界、不可部署;production 庫
才是出賽組態);(iii) 檢索量本身不是解方:production 庫上 k=5→100 端到端全距僅 1.3 點且非單調;
legacy 庫上 k=50→100 飽和(95.1/95.6→95.6)——歷史觀察到的「k=100 回歸」
(95.3→94.9)重測未重現,屬單次噪音,「多餘例句是干擾項」的強主張應撤回,正確
描述是**快速飽和、無單調收益**;(iv) 失敗案例中 73–99%
的正確 op 已在 context 內【歷史值】。綜合:**瓶頸是近義 intent 的辨別;檢索的角色
是把弱模型拉進可辨別區,而非直接決定答案**。工程上的推論:同庫同設定下換模型值
+8.5 點(97.4 vs 88.9),比任何檢索後端工程(±0.4 點【歷史值】)大一個數量級;
stdlib BM25 與 dense/hybrid 端到端相當(1,420 句差 1 句【歷史值】)而延遲低
30–80 倍、部署面乾淨(無 ONNX/glibc 面)。

### 4.5 監督式分類器 baseline:LLM 可以被取代嗎?

【Table 3 placeholder:分類器 × 協定 × op 準確率】

若路由只是 71 類分類問題,一個免 API、微秒級延遲的監督式分類器理應勝任。我們以
兩種協定測試(皆 leave-one-case-out;分類器僅預測 op、不抽 params,比較已對 LLM
不利):(a) 資源對齊——訓練資料限於 LLM 檢索可見的 940 列公開庫;(b) 全資料——
公開庫 + 全部標註句(約 2,230 列/fold)。結果:

| 模型 | (a) 資源對齊 | (b) 全資料 |
|---|---|---|
| TF-IDF + LogReg | 32.3% | 48.5% |
| TF-IDF + LinearSVC | 44.7% | **73.3%** |
| BM25 top-1 | **47.4%** | 70.9% |
| BM25 vote@5 | 32.5% | 56.6% |
| SBERT emb + kNN top-1(E1b) | **55.1%** | 72.8% |
| SBERT emb + LogReg(E1b) | 27.5% | 33.9%(off-protocol 調參上限 76.3%) |
| LLM 管線(參考,production 庫) | — | **88.9%**(gpt,N=5)/ **97.4%**(haiku) |

即使用盡全部標註資料,最強分類器(73.3%)仍落後部署組態的 gpt 管線 15.6 點、落後
haiku 24.1 點;其混淆對與 LLM 屬同一批近義家族、錯誤率約 10 倍。更強的語義表徵也
救不了:凍結 SBERT embedding 的最佳組合 72.8%(kNN top-1,協定 b)比 TF-IDF+
LinearSVC 低 0.5 點,off-protocol 調參上限亦僅 76.3%(E1b)。協定 (a) 中 3 個 intent 因庫中零樣本而結構性不可達
(上限 95.8%),而 LLM 靠常駐 catalog 永遠可達——再次支持 *retrieve
demonstrations, not the tool list*。附帶發現:kNN 多數決(vote@5)在兩協定皆
**劣於** top-1——庫去重後正確配對只出現一次,近鄰被混淆 intent 填滿;這解釋了
為何例句應作為「示範」交給 LLM 辨別,而非直接投票。

### 4.6 Fault-injection:損害上限的實證檢驗

【Table 4 placeholder:6 測資 × 污染模式 → caught / drift / escaped;修正前後】

我們在 dispatch 層(即路由輸出的落點)注入污染,模擬 LLM 的最壞輸出:錯誤數值
參數(k±1)、錯誤 basis、目標改指到**另一個存在的** net、整個 intent 掉包、以及
繞進引擎內部的 function-changing rewire。6 個 transform-heavy 公開測資、24 次
注入(另 6 次乾淨 baseline 全過):

- **Caught 14/24**:3 次 guard 回滾(ABC cec 攔下全部 function-breaking 污染,
  快照位元精確還原)、2 次封閉世界拒絕(basis 不在值域)、9 次 benign(污染後的
  變更仍滿足原句全部硬性要求)。
- **Drift 7/24**:結果網表功能等價且結構合法,但違反**原句**的結構/basis 要求——
  guards 執行的是「被污染的合約」,不是使用者的句子;回應並宣稱成功。這是誠實的
  架構邊界:fail-closed 擋的是**不安全**,不是**不如所求**。
- **Escaped 3/24(修正前)**:同一根因——改名(rename)被假設為「純外觀操作」而
  未走 guard,將 `new` 填成**既有** net 名會把兩個 driver 融合成雙驅動網,產出
  非等價網表且回應宣稱成功。其中一例 ABC 對雙驅動網回 NA,連既有 evaluator 的
  等價檢核都放行(評測器盲點)。修正為一行碰撞檢查(拒絕改名到既有名稱)後重驗:
  **24/24 零不安全 commit**,§3.4 的主張成為 exact;修正並通過全部 40 個公開
  測資的完整回歸(HARD 84/84;既有的 GOLDEN/DERIVED 差異經 main 對照確認與本
  修正無關)。

這個實驗把架構敘述轉成可檢驗的命題,同時誠實暴露兩件事:guard 的語意邊界(drift
類),以及「假設某操作無害」是 fail-closed 架構的典型漏洞來源(rename 案例)。

### 4.7 量測效度(側記)

本節所有數字背後有一層效度工程,源自兩次真實事故。其一:共享額度下的並發評測
觸發 rate limiting,client 的優雅降級把 458 句 LLM 呼叫靜默轉為 no-op,產出看似
完全合理的 67.2%(同設定真值 97.8%)——**基礎設施失敗偽裝成模型失敗**,且無法
從分數本身察覺。其二:validator 對畸形 LLM 輸出(dict 型 enum 參數)崩潰、整輪
作廢——在 fail-closed 架構裡,驗證器必須比被驗證者更健壯。對策與紀律:降級呼叫
計數器 + 任何降級即判 INVALID RUN(其後在真實額度耗盡中第二次攔截)、評測輪跨輪
嚴格串行、檢索 LOCO 衛生、答案三方獨立重算(646 PASS / 0 FAIL / 34 SKIP)。
一句話:**量測基礎設施需要與被量測系統同等的工程紀律**。

## 6. Limitations 與 Threats to Validity

(1) 單一 testbed:1,420 句來自單一任務的語彙;方法的 transfer(如 OpenROAD 指令
路由)尚未驗證【TODO:E9】。(2) haiku 主線數字(97.4%,k=50)已重驗但 N=1;歷史 pre-dedup 值 97.8
僅用於 §4.7 的事故配對敘述。(3) gpt-4o-mini 主線 N=5(全距 ≤0.6 點)、legacy 庫 N=2;haiku N=1,補跑中。(4) 混合路由劣於純 LLM 的結論基於單一
split。(5) 資料集釋出取決於主辦方授權【TODO:行政】。(6) drift 類損害(§4.6)
顯示 guards 的保證以「污染後的合約」為界,句子層級的意圖一致性需要另一層驗證。
(7) 本研究以雲端 mini 級模型作為「可本地部署小模型」regime 的**能力代理**;開源
權重模型(7–14B)的直接驗證為後續工作【TODO:E8,general framing 下優先級上升】。

## 7. Conclusion

在 all-or-nothing 的環境裡,LLM 代理的正確性不該押在事後驗證的覆蓋率上,而應該
由架構保證:把 LLM 關進表達不出不安全操作的封閉世界,把一切變更擋在等價證明之後。
這個架構不只守住了零硬性違規,還把「小模型的路由極限」變成一個可以乾淨量測的
問題——答案是:瓶頸在近義 intent 的辨別,檢索與分類器都不是解方,而評測本身的
效度需要與系統同等的工程紀律。
